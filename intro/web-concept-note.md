# 📘 [Full-Scale] 웹 아키텍처 비전공자 마스터 가이드 & 퍼널 데이터 트래킹

## 1. 브라우저 저장소의 모든 것 (Storage & Session)

HTTP 프로토콜은 단기 기억상실증(**Stateless**) 상태이므로, 브라우저가 유저의 상태를 기억해 줄 주머니들이 필요합니다. 개발할 때 "이 데이터 어디 저장해요?"라고 할 때 꺼내는 카드들입니다.

### 🗂️ 저장소 스펙 비교 테이블

| 비교 항목 | 쿠키 (Cookie) | 로컬스토리지 (LocalStorage) | 세션스토리지 (SessionStorage) |
| --- | --- | --- | --- |
| **저장 위치** | 사용자의 브라우저 (서버 전송용) | 사용자의 브라우저 (기기 내부 고정) | 사용자의 브라우저 (임시 저장용) |
| **용량 제한** | 개당 **4KB** 미만 (매우 작음) | 약 **5MB ~ 10MB** (넉넉함) | 약 **5MB** (넉넉함) |
| **유지 기간** | 개발자가 설정한 만료일(Expire Date)까지 | 사용자가 캐시를 지우기 전까지 **영구적** | **브라우저 탭/창을 닫으면 즉시 삭제** |
| **네트워크 전송** | 모든 HTTP 요청마다 **헤더에 자동 포함**됨 | 서버로 자동 전송 안 됨 (코드로만 호출) | 서버로 자동 전송 안 됨 (코드로만 호출) |
| **보안 스펙** | `HttpOnly`, `Secure` 옵션으로 탈취 방지 가능 | 자바스크립트(`XSS` 공격)로 쉽게 털릴 수 있음 | 자바스크립트(`XSS` 공격)로 쉽게 털릴 수 있음 |
| **현업 실무 용도** | 로그인 세션 토큰, 7일간 이 팝업 보지 않기 | **비로그인 유저 임시 ID**, 다크모드, 장바구니 | 은행 로그인 타임아웃, 글쓰기 임시 임력 폼 |

### 💡 실무 기획 포인트: 비로그인 장바구니 로직 설계하기

1. 유저가 비로그인 상태로 상품을 장바구니에 담으면 브라우저의 `LocalStorage`에 상품 ID와 수량을 배열 형태로 저장합니다.
2. 유저가 나중에 로그인이나 회원가입을 완료하면, 프론트엔드가 `LocalStorage`에 남아있던 장바구니 데이터를 긁어와서 백엔드(DB)로 쏘아주며 "이 비로그인 데이터, 방금 로그인한 계정 장바구니에 합쳐줘(Merge)"라고 API를 호출하는 방식으로 설계합니다.

## 2. 회원 인증 패러다임 (Authentication)

유저가 "나 회원이야!"라고 주장할 때, 웹 서비스가 이를 신뢰하고 마이페이지나 결제 권한을 열어주는 메커니즘입니다.

### ① 세션/쿠키 방식 (전통적인 State-ful 서버 방식)

1. 유저가 아이디/비밀번호를 입력하고 로그인 요청을 보냅니다.
2. 서버가 DB를 확인한 뒤 회원 정보가 맞으면, 서버 메모리(세션 저장소 또는 Redis)에 방을 하나 파고 `Session ID (예: abcd1234)`를 생성합니다.
3. 이 `Session ID`를 브라우저에게 **쿠키(Cookie)** 주머니에 담아서 돌려줍니다.
4. 브라우저는 다음부터 사이트 내의 다른 페이지로 이동할 때마다 이 쿠키(ID 카드)를 요청에 자동으로 얹어서 보냅니다.
5. 서버는 요청이 올 때마다 자기 메모리방을 뒤져서 "어, abcd1234방 있네? 들어와" 하고 인증해 줍니다.

* **장점:** 서버가 모든 로그인 권한을 통제하므로, 특정 유저가 악질적인 행동을 하면 서버단에서 세션을 강제 종료(강제 로그아웃) 시킬 수 있습니다.
* **단점:** 동시 접속자가 수만 명이 되면 서버 컴퓨터의 메모리가 터져나갑니다. 서버를 3~4대로 늘리면 "1번 서버에 로그인했는데 2번 서버로 접속하니까 로그인이 풀리는" 대참사가 나서 세션 공유 전용 서버를 따로 구축해야 합니다.

### ② JWT (JSON Web Token) 방식 (모던 크로스 플랫폼 대세 방식)

1. 유저가 로그인하면 서버는 세션방을 파지 않습니다. 유저 고유 정보(예: `user_id: 50, name: '민주'`)를 가져와서, 서버만 알고 있는 고유의 '비밀키(Secret Key)'로 단단히 밀봉한 암호화 압축 문서인 토큰(Token)을 발행합니다.
2. 이 토큰을 프론트엔드로 던져주면, 프론트엔드는 이를 주로 `LocalStorage`나 웹용 `Cookie`에 저장합니다.
3. 이후 마이페이지 조회 등의 API를 호출할 때, 헤더 스펙 중 하나인 **`Authorization: Bearer <토큰문자열>`** 공간에 이 토큰을 끼워 보냅니다.
4. 서버는 메모리를 뒤질 필요 없이, 들고 온 토큰을 자신의 비밀키로 해독(디코딩)해 봅니다. 도장이 위조되지 않았다면 "아, 50번 유저 민주 맞구나" 하고 데이터를 즉시 넘겨줍니다.

* **장점:** 서버가 로그인 상태를 기억할 필요가 전혀 없으므로(**Stateless**), 서버를 수십 대 복사해서 늘려도 아무런 무리가 없습니다. 앱(App)이나 다른 웹 서비스(OAuth 연동 등)와 권한을 공유할 때도 매우 유연합니다.
* **단점:** 토큰 자체가 입장권이기 때문에 해커에게 털리면 만료될 때까지 속수무책입니다. 이를 보완하기 위해 수명이 30분짜리인 `Access Token`과, 이를 갱신해 주는 수명이 2주짜리인 `Refresh Token`을 조합하는 이중 토큰 구조를 필수적으로 사용합니다.

## 3. 백엔드와의 소통 통로, REST API & HTTP 스펙

### 🌐 HTTP Method 설계 (현업 표준 규칙)

URI(주소명)는 무조건 **명사형태**로만 짓고, 행위(동사)는 **HTTP 메서드**를 통해 서버에 전달해야 협업할 때 커뮤니티가 꼬이지 않습니다.

* **`GET` (조회/Read):** 서버의 데이터를 가져올 때만 사용합니다.
* 주소 구조: `GET /products` (상품 전체 목록 조회), `GET /products/102` (102번 상품 상세 조회)
* 특성: 브라우저 주소창에 데이터가 다 노출되므로 로그인 비밀번호 전송 등에는 쓰면 안 됩니다.


* **`POST` (생성/Create):** 서버에 완전히 새로운 데이터를 등록할 때 사용합니다.
* 주소 구조: `POST /users` (회원가입 요청), `POST /orders` (새로운 주문 생성)
* 특성: 데이터가 URL 주소창이 아닌 패킷의 본문(Body) 깊숙한 곳에 숨겨져 전송되므로 비교적 안전합니다.


* **`PUT` (전체 수정) / `PATCH` (일부 수정) [Update]:** 데이터를 고칠 때 씁니다.
* 주소 구조: `PATCH /users/50` (50번 유저의 닉네임만 변경)


* **`DELETE` (삭제/Delete):** 데이터를 날릴 때 씁니다.
* 주소 구조: `DELETE /cart/items/p001` (장바구니에서 p001 제품 제거)



### 🔢 실무자용 HTTP 상태 코드 가이드 (Status Code)

로그인 버튼을 눌렀는데 화면에 아무 변화가 없거나 엉뚱한 창이 뜰 때, 키보드 `F12`를 눌러 네트워크 탭의 이 숫자를 보고 범인을 검거합니다.

* **`200 OK`:** 가져오기, 수정하기, 삭제하기 등이 완벽하게 성공함.
* **`201 Created`:** 회원가입이나 글 작성이 완벽하게 서버 DB에 생성됨.
* **`400 Bad Request`:** 프론트엔드 잘못. 서버가 요구하는 필수 데이터(예: 비밀번호 필수조건 등)를 누락하고 폼을 제출했을 때 뜸.
* **`401 Unauthorized`:** 로그인 정보가 없거나, 만료된 토큰을 들고 인증이 필요한 주소에 비벼볼 때 백엔드가 뱉는 거절 코드.
* **`403 Forbidden`:** 로그인은 되어 있으나 접근 권한이 없음. (예: 일반 회원 계정으로 `/admin` 관리자 페이지 API 호출할 때 뜸).
* **`404 Not Found`:** 존재하지 않는 API 주소를 때렸거나, 이미 삭제된 게시글 주소로 들어갔을 때 브라우저가 길을 잃은 상태.
* **`500 Internal Server Error`:** 백엔드 개발자의 소스코드가 예외 처리를 못 하고 서버 내부에서 폭발했을 때 발생. (프론트엔드 기획/UI 잘못이 아님).
* **`502 Bad Gateway` / `503 Service Unavailable`:** 서버 컴퓨터의 트래픽이 폭주하여 죽었거나, 인프라 배포 설정이 꼬여서 게이트웨이가 막힌 상태.

## 4. 인프라 인젝션 (Infrastructure)

코드가 작동하는 서버 공간과 인간이 타이핑하는 텍스트 주소판이 어떻게 연결되는지에 대한 구조입니다.

* **IP 주소 (Internet Protocol Address):** 컴퓨터가 서로를 알아보기 위한 고유의 네트워크 주민등록번호 숫자 주소 (예: `13.125.10.45`).
* **도메인 (Domain Name):** 숫자를 외우기 힘드니 인간의 언어로 치환한 명패 (예: `piora.com`). 가비아 같은 레지스트라 도메인 대행업체에서 연간 비용을 지불하고 소유권을 대여합니다.
* **DNS (Domain Name System):** 유저가 `piora.com`을 주소창에 치면 도메인 대행사에 등록해 둔 "네임서버 IP 주소판"을 확인하여 `13.125.10.45` 컴퓨터로 유저의 내비게이션을 꺾어주는 전화번호부 매핑 시스템입니다.
* **SSL / HTTPS (Secure Sockets Layer):** 클라이언트와 서버 사이의 통신 데이터를 가로채지 못하게 암호화 터널을 개설하는 보안 프로토콜 규격입니다. 인증서가 적용되면 주소창 왼쪽에 자물쇠🔒 아이콘이 뜨며, 요즘 브라우저는 SSL이 없는 사이트를 보안 취약 사이트로 간주해 차단 처리를 때립니다.

## 5. [핵심] 데이터 퍼널 분석을 위한 소스 트래킹 (Funnel Analytics & Tracking)

쇼핑몰이나 B2B 서비스를 만들 때 **"유저가 인스타그램 광고를 보고 들어왔는지?", "네이버 블로그 링크를 타고 왔는지?", "어디서 이탈했는지?"** 추적(Tracking)하기 위한 기획과 데이터 수집 설계 스펙입니다. GA4(구글 애널리틱스)나 앰플리튜드 같은 분석 툴을 붙이기 전에 원리를 알아야 합니다.

### ① UTM 파라미터 (Utm Parameter) 방식 (외부 유입 소스 추적)

외부 마케팅 채널이나 광고 소스에서 우리 사이트로 유저를 보낼 때 주소창 뒤에 일정한 규칙을 가진 꼬리표 파라미터를 달아서 유입 경로를 추적하는 전 세계 표준 규격입니다.

* 주소 예시: `https://piora.com/?utm_source=instagram&utm_medium=cpc&utm_campaign=26ss_launching`

#### 🏷️ UTM 필수 소스 5가지

1. **`utm_source` (유입 채널):** 유저가 어디서 왔는가? (값 예시: `instagram`, `naver`, `google`, `newsletter`)
2. **`utm_medium` (마케팅 매체):** 어떤 방식의 매체인가? (값 예시: `cpc`-유료광고, `organic`-자연검색, `email`-이메일 링크)
3. **`utm_campaign` (캠페인 이름):** 어떤 마케팅 목적인가? (값 예시: `26ss_launching`, `chuseok_sale`)
4. **`utm_term` (키워드):** 검색 광고 시 어떤 키워드를 쳤는가? (값 예시: `리본 가디건`, `봄 자켓`)
5. **`utm_content` (콘텐츠 종류):** 동일 광고 내에서 어떤 시각 소재/A-B 테스트용인가? (값 예시: `banner_pink`, `video_mood`)

#### ⚙️ 프론트엔드 수집 로직 원리

유저가 저 주소를 타고 들어오면, 프론트엔드 자바스크립트는 주소창의 파라미터(`URLSearchParams`)를 긁어내어 **`LocalStorage`에 저장**해 둡니다. 유저가 사이트를 돌아다니다가 최종적으로 `회원가입`이나 `주문하기` 버튼을 누를 때, 로컬스토리지에 숨겨져 있던 UTM 값들을 꺼내 백엔드 데이터베이스로 같이 쏘아줍니다. 이렇게 해야 "인스타그램 핑크 배너 광고를 보고 들어온 사람이 실제로 결제까지 완료했다"는 매출 전환 데이터 매핑이 성립됩니다.

### ② 내부 전환 퍼널 분석 (Internal Funnel Analytics)

쇼핑몰 서비스의 표준 전환 퍼널 단계는 보통 다음과 같이 쪼개집니다. 각 단계의 이탈률을 계산하는 것이 그로스해킹과 데이터 분석의 기초입니다.

> **[홈 화면 접속] ➡️ [상품 카테고리/목록 조회] ➡️ [상품 상세페이지 조회] ➡️ [장바구니 담기] ➡️ [주문서 작성 단계] ➡️ [결제 완료]**

#### 🛠️ 퍼널 데이터 수집을 위한 이벤트 로그 설계서 (Spec Sheet)

분석 툴이나 자체 로그 시스템을 구축할 때, 유저가 특정 행동을 할 때마다 아래의 형태처럼 '유저 데이터 + 행동 데이터(속성값)'를 패킷으로 구성해서 서버로그로 적재해야 합니다.

```json
{
  "user_id": "guest_1716030000",          // 유저 식별값 (로그인이면 회원고유ID)
  "event_name": "click_add_to_cart",       // 명확한 행동 규격 이름
  "timestamp": "2026-05-18T20:10:51Z",    // 이벤트 발생 정확한 시각
  "device_os": "MacOS",                   // 디바이스 환경
  "properties": {                         // 해당 행동 시점의 구체적인 컨텍스트 속성
    "product_id": "p001",
    "product_name": "26SS Ribbon Cardigan",
    "price": 129000,
    "quantity": 2,
    "current_page": "product_detail",
    "inflow_source": "instagram"          // 로컬스토리지에 보관해 둔 최초 유입 UTM 소스 매핑
  }
}

```

이러한 로그 데이터를 유저가 버튼을 클릭할 때마다 깃허브나 로그 서버로 실시간 적재(POST 요청)해 주면, 엑셀이나 앰플리튜드 툴에서 **"상품 상세 조회까지는 1,000명이 왔는데 장바구니 담기는 왜 50명밖에 안 했지? 상세페이지 가독성이나 가격에 문제가 있나?"** 같은 퍼널 데이터 분석과 비즈니스 의사결정이 가능해집니다.
